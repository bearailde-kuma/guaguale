# 迭代开发指南

## 分层原则

`Catalog` 只读配置；`Economy` 只计算奖池；`Game` 持有唯一状态并处理数值事务；UI 只发送意图和表现结果。不要在界面里直接改钱包、精神和收藏，测试专用演示除外。

`changed` 驱动 UI 刷新，`ticket_settled` 驱动中奖反馈，`notice` 显示事务失败原因。活动动画结束后才提交数值。动画期间阻止再次触发交易；退出时尚未完成的活动不收费。

玩法 RNG 独立于粒子、音效。存档将 RNG 的 64 位 seed/state 保存为十进制字符串，避免 JSON 数字精度损失。

## 修改配置

- 彩票：`id` 必须稳定。`price` 为整数；`cells` 为正整数；`columns` 控制列数；`chance` 为 0–1；`jackpot` 是大奖票价倍率；新票同时满足累计奖金、刮票张数才能解锁。
- 奖池：`payout_weights` 五项总和必须为 100；前四项对应 `payout_multipliers`，第五项使用票种 `jackpot`。
- 技能：本版三个技能规则在 `game_state.gd`，成本、名称、解锁在 JSON。增加第四个技能还需扩充 `skill_error/use_skill`、快捷键与 UI 布局。
- 聚财：`upgrade_costs`、`upgrade_gates` 长度应相同；`resonance_factor` 控制每级倍率。
- 资产：`id` 不要随意更名；按数组顺序解锁。`spirit` 叠加上限；`fortune` 是加法财运，所有资产加成求和后再乘聚财。
- 活动：`restore` 是恢复量，超过上限会截断；本版超过 9000 的值在 UI 显示为全恢复。

当前 UI 为五种票、三技能、十资产、十二级升级做了固定布局。调数值直接改 JSON；扩展数量时需要同时改布局和测试。没有把固定数量伪装成完全无限扩展的内容系统。

## 替换素材

目前场景、车房、硬币用 `PixelArt` 与 `CanvasItem` 绘制，没有第三方贴图依赖。正式制作可以逐步用 `TextureRect`、`Sprite2D`、`AnimationPlayer` 替换表现层，保持 `Game` 的事务接口不变。

字体原文件保留完整中文字符集，方便新增文案。建议使用 12 / 24 / 36 像素字号；18 像素是小界面的空间折中。后续高精度 UI 可改双分辨率字体布局。

## 存档兼容

当前 schema=1。新字段提供默认值，删除或重命名 `asset.id` 必须写迁移。不要直接修改既有 `current` 彩票的奖金；已购票必须保留当时结果。

保存先写 `.tmp` 并 flush，再用 rename 替换；只有通过校验的旧主存档才会复制到 `.bak`。读取失败先回退备用存档。首版不支持云存档、多槽位或导入旧项目存档。

## 验证

1. 运行核心回归检查，确认兑奖一次性、技能前置条件、部分刮擦锁定、存档恢复、破产兜底与终局。
2. 改数值后运行 100 种子模拟，更新 `balance-report.json` 和设计文档中的实测摘要。
3. 用 Godot 实际打开主场景，至少试一次拖动刮擦、切换票种、买资产、活动和重新启动。
4. 有显示环境时可以运行 `godot --path . -- --smoke`，生成开始、中奖、资产、生活和五档票截图。该模式不读写正常存档。
5. 导出后再运行导出包，避免 JSON 配置遗漏在 PCK 之外。导出预设已显式包含 `data/*.json`。

## 建议下一版

- 将 `main.gd` 的模态菜单进一步拆为独立场景，支持手柄焦点和不同画面比例。
- 为五种票增加不同中奖规则，例如三同图案、幸运号码匹配，而不只是不同格数。
- 增加更丰富的旅行与购车过场、环境音乐、招财猫和店员表现。
- 记录匿名本地试玩统计，先由玩家自愿导出，再判断节奏是否需要调整。
- 在做转生系统前，先验证这条完整单局路线是否好玩；首版以明确结局收束。
